# Локальная доработка AI Атрибутов — v28

Источник регрессии: `/Users/alexandr/Desktop/pipeline_report.json`. GitHub, commit, push и deploy не выполнялись. Остальные продукты не изменялись.

## Выполнено

1. Контакт относительно события: `event_anchor` содержит временную формулировку последнего согласованного события, цитаты и `offset_minutes`. День и время события рассчитывает код, затем прибавляет смещение. Показ завтра в 15:00 и звонок за час до него дают завтра в 14:00. Дата показа отдельно не становится датой контакта.
2. Next Contact Extractor использует strict schema `application_next_contact_date_extractor_v3`. Judge проверяет время события, его перенос, смещение и цитаты, не меняя значение. Прочие модельные схемы остаются v2; Gate и CRM обновлены до v3. Внешнее имя существующего модуля contract-v2 сохранено для совместимости загрузки.
3. `normalization_status` вычисляется только кодом: resolved, missing_reference, unresolved, not_applicable. Отсутствие creation time сохраняет найденную договорённость, но не создаёт календарную дату. Эти состояния не считаются невалидным JSON и не запускают повторы LLM.
4. Если Judge принял договорённость, а дату рассчитать нельзя, Gate/CRM сохраняют `pending_attributes` и `next_contact_resolution` с причиной, цитатой и событием. Дата остаётся null, действие SKIP, статус PARTIAL_READY. Это отличается от not_determined: смысл найден, календарное значение ещё не готово.
5. Готовый серверный fallback сохраняется как KEEP_FALLBACK/source=fallback; он не превращается в AI-договорённость. Найденная договорённость и причина незавершённого расчёта остаются в отдельном next_contact_resolution. Подтверждённый отказ блокирует подстановку fallback и даёт NO_CONTACT. Studio не создаёт новый таймер +24 часа.
6. UI показывает «Договорённость найдена — дата не рассчитана», причину и цитату. Сводка использует PARTIAL_SUCCESS/«Частичный успех» и передаёт business_pipeline_status. Ошибка одного атрибута не прекращает обработку остальных. Метрика готовности CRM учитывает незавершённые даты.
7. Миграция v27 → v28 сохраняет пользовательские промпты и настройки, добавляет новые правила один раз. Исходный конфиг резервируется в Local Storage: `pipelineLabV3.pipelineConfig.<projectId>.before-v28`. История не переписывается.

Без точного времени события дата контакта не рассчитывается от технического ориентира 10:00. Неподдерживаемая формулировка сохраняется для уточнения без дополнительных запросов к модели. Для корректного JSON с неподдерживаемым временем число повторов равно 0; реальные ошибки JSON по-прежнему могут повторяться.
