## 1. Общая архитектура pipeline

Целевой pipeline фиксируется как **5 смысловых AI-этапов**, без дополнительных проверяющих моделей между ними:

```
Валидированная транскрибация
        ↓
1. Факты и цитаты
        ↓
2. Потребности клиента
        ↓
3. Результат звонка и следующий шаг
        ↓
4. Генерация summary
        ↓
5. Summary Quality Gate
        ↓
Отображение / ручная оценка / сохранение в CRM
```

**Ключевой архитектурный принцип.** Первые три этапа независимо извлекают данные из транскрибации. Summary Agent получает результаты всех трёх этапов и транскрибацию. Quality Gate оценивает готовое summary по тем же критериям и шкале, что и человек. Отображение и сохранение в CRM — это не AI-этапы pipeline, а технический слой публикации результата (в MVP — запись в историю запусков Песочницы/Дашборда, реальной интеграции с внешней CRM нет).

| № | Этап | Основная задача | Источник | Результат |
|---|---|---|---|---|
| 1 | Факты и цитаты | Зафиксировать подтверждённые факты разговора и важные высказывания клиента | Транскрибация | `facts.json` |
| 2 | Потребности | Выявить полный клиентский запрос, требования, ограничения и атрибуты | Транскрибация + факты | `needs.json` |
| 3 | Результат и следующий шаг | Определить итог разговора, договорённости и действия сторон | Транскрибация + факты | `outcome.json` |
| 4 | Summary Generator | Создать короткое человеческое summary | Три JSON + транскрибация | `summary.json` |
| 5 | Quality Gate | Оценить summary по единой человеко-AI методике | Summary + три JSON + транскрибация | `quality_report.json` |

Что важно: этапы 1–3 не должны генерировать готовое summary, оценивать качество друг друга, переписывать транскрибацию, исправлять данные другого этапа или возвращать общий Quality Score. Каждый этап отвечает только за свой смысловой блок.

## 2. Этап 1. Извлечение фактов и цитат

**Цель.** Получить точный набор значимых фактов, которые реально прозвучали в разговоре. Это не пересказ разговора и не готовое summary.

**Факты о клиенте и запросе:** цель обращения, объект/тип объекта, назначение покупки, бюджет, способ финансирования, срок покупки, локации, параметры объекта, готовность к просмотру, возражения, ограничения, важные обстоятельства, предпочитаемый канал связи.

**Важные цитаты** — только те, что подтверждают: ключевую потребность, бюджет/финансирование, срок, мотивацию, возражение, готовность к действию, договорённость. Не извлекать цитаты с адресом объекта, приветствиями или техническими деталями без продуктовой ценности.

**Формат результата**

```json
{
  "facts": [
    {
      "id": "fact_001",
      "category": "budget",
      "value": { "min": null, "max": 5500000, "currency": "RUB" },
      "normalized_text": "Бюджет клиента — до 5,5 млн ₽",
      "speaker": "client",
      "evidence": [{ "turn_id": 24, "quote": "До пяти с половиной рассматриваю" }],
      "confidence": 0.99,
      "status": "confirmed"
    }
  ],
  "quotes": [
    { "id": "quote_001", "category": "objection", "speaker": "client", "text": "Девять шестьсот ежемесячно — дороговато", "turn_id": 38, "importance": "high" }
  ],
  "conflicts": [],
  "missing_critical_facts": ["purchase_timeline", "funding_source"]
}
```

**Правила этапа.** Не добавлять факты по логике или контексту. Не считать слова агента потребностью клиента без подтверждения клиента. Разделять: подтверждённый факт / предположение / предложение агента / незакрытый вопрос. Каждому важному факту — evidence. Если информация не определена — явно не включать (`not_found`), а не угадывать. Если в разговоре есть конфликтующие значения — сохранять оба и помечать конфликт.

## 3. Этап 2. Извлечение потребностей клиента

**Цель.** Собрать не отдельные реплики, а полноценную модель клиентского запроса. Этап отвечает на вопрос: что клиент реально хочет, что для него важно и что мешает двигаться дальше?

**Структура потребности**

```json
{
  "primary_need": { "intent": "buy", "object_type": "land_plot", "purpose": "personal_use", "summary": "Клиент рассматривает покупку участка ИЖС для строительства дома" },
  "requirements": {
    "locations": ["Мистолово", "Капитолово", "Лаврики"],
    "budget": { "max": 5500000, "currency": "RUB" },
    "object_parameters": [
      { "parameter": "land_category", "value": "ИЖС", "priority": "must_have" },
      { "parameter": "land_area", "operator": ">=", "value": 6, "unit": "соток", "priority": "must_have" }
    ],
    "preferences": [],
    "limitations": ["Не устраивает высокий ежемесячный взнос"]
  },
  "decision_context": { "motivation": null, "purchase_timeline": "не определено", "funding_source": "не определено", "readiness": "рассматривает варианты", "decision_stage": "active_search" },
  "canonical_attributes": { "needs": ["Строительство"], "funding_source": "не определено", "purchase_timeline": "не определено" },
  "evidence_links": ["fact_001", "fact_004", "quote_001"],
  "confidence": 0.96
}
```

**Обязательная часть:** основное намерение, тип объекта, цель, бюджет, локация, обязательные требования, желательные параметры, ограничения, возражения, стадия принятия решения, готовность к действию.

**Канонические атрибуты** возвращаются отдельно, строго по утверждённым справочникам (пример: `needs: ["Новостройки", "Ипотека", "Строительство"]`).

**Основной риск этапа** — не различить типы информации:

| Тип информации | Пример |
|---|---|
| Потребность клиента | «Нужен участок от шести соток» |
| Предложение агента | «Могу предложить участок на пять соток» |
| Характеристика обсуждаемого объекта | «Этот участок — 6 соток» |
| Условие клиента | «Если взнос меньше, готов рассматривать» |
| Незакрытый вопрос | «Надо уточнить, входит ли НДС» |

Если это не разделить, в потребности начинают попадать характеристики одного объекта, предложения агента и неподтверждённые предположения.

## 4. Этап 3. Результат звонка и следующий шаг

**Цель.** Определить: чем фактически закончился разговор, что было согласовано, кто должен выполнить действие, что происходит дальше с заявкой.

**Структура результата**

```json
{
  "conversation_outcome": {
    "type": "follow_up_required",
    "summary": "Клиент продолжает рассматривать покупку после получения дополнительной информации",
    "client_status": "interested_with_conditions",
    "resolved_questions": [],
    "unresolved_questions": ["Точный размер эксплуатационных расходов", "Коммунальные платежи", "Включён ли НДС"]
  },
  "agreements": [
    {
      "id": "agreement_001",
      "owner": "agent",
      "action": "уточнить расходы и статус НДС у собственника",
      "deadline": { "value": "сегодня или завтра", "normalized": null },
      "channel": "WhatsApp",
      "status": "agreed",
      "evidence": { "turn_id": 46, "quote": "Я уточню у собственника и напишу вам сегодня или завтра в WhatsApp" }
    }
  ],
  "next_step": {
    "primary": { "owner": "agent", "action": "уточнить информацию и связаться с клиентом", "deadline": "сегодня или завтра", "channel": "WhatsApp" },
    "client_commitment": null,
    "is_specific": true,
    "is_agreed": true
  },
  "conversation_closed": false,
  "confidence": 0.98
}
```

**Классификация результата** (компактный справочник): `viewing_agreed`, `meeting_agreed`, `follow_up_required`, `information_sent`, `selection_preparation`, `client_will_decide`, `client_not_ready`, `object_not_suitable`, `request_closed`, `no_agreement`.

**Важное разграничение** — три сущности нельзя объединять в одно поле:
- **Результат разговора** — что изменилось по итогам звонка.
- **Договорённость** — что стороны согласовали.
- **Следующий шаг** — что конкретно должно произойти дальше.

## 5. Этап 4. Генерация summary

**Источники.** Summary Agent получает `transcript`, `facts`, `needs`, `outcome`, `crm_context.fields_already_visible` (поля, уже видимые в карточке CRM — их не нужно дублировать).

**Приоритет источников.**
1. **JSON предыдущих этапов** — основной источник фактов, потребностей, ограничений, результата, договорённостей, следующего шага, цитат.
2. **Транскрибация** — используется для понимания общего контекста, естественной формулировки, проверки связности, точного воспроизведения цитат, разрешения неоднозначности. Транскрибация НЕ должна разрешать Summary Agent: добавлять новые факты, которых нет в JSON; самостоятельно менять потребность; самостоятельно определять новый следующий шаг; считать предложение агента согласованной договорённостью.

**Правило расхождения.** Если транскрибация содержит важный факт, которого нет в JSON:

```json
{ "summary_status": "input_data_incomplete", "missing_fact": { "description": "В транскрибации указан срок покупки, но он отсутствует в needs.json", "turn_id": 42 } }
```

Summary Agent не должен молча использовать такой факт — иначе исчезает управляемость pipeline.

## 6. Формат итогового summary

- **Итог разговора** — связный деловой текст на 2–4 предложения.
- **Ключевые факты** — до 4 наиболее полезных фактов.
- **Важные цитаты** — до 2 цитат клиента, только когда они действительно передают позицию, ограничение или готовность.
- **Договорённости / следующий шаг** — одно предложение.

Пример:

> **Итог разговора.** Клиент рассматривает покупку участка ИЖС от 6 соток в районе Мистолова с бюджетом до 5,5 млн ₽. Обсудили участок в КП «Охтинское Раздолье»; клиента смущает ежемесячный взнос 9 600 ₽. Клиент продолжает рассматривать варианты и заинтересован в дополнительных предложениях в Мистолове, Капитолове и Лавриках.
>
> **Ключевые факты.** Участок ИЖС от 6 соток · Бюджет — до 5,5 млн ₽ · Приоритетные локации — Мистолово, Капитолово и Лаврики · Основное возражение — ежемесячный взнос 9 600 ₽.
>
> **Важная цитата.** «Девять шестьсот ежемесячно — дороговато».
>
> **Договорённости / следующий шаг.** Агент отправит видеообзор и подберёт альтернативные участки для клиента в MAX.

## 7. Требования к тексту «Итог разговора»

| Параметр | Требование |
|---|---|
| Объём | Обычно 2–4 предложения |
| Стиль | Деловой, простой, естественный |
| Читаемость | Понятно без повторного чтения |
| Фокус | Зачем обратился, что выяснили, что важно, чем закончили |
| Пересказ | Запрещён покадровый пересказ |
| Дубли карточки | Не включать без необходимости |
| Неизвестные данные | Не выводить |
| Формулировки | Без канцелярита и сложных конструкций |

**Правило адаптивного объёма:** очень короткий/одна тема — 2 предложения; стандартный звонок — 3 предложения; сложный звонок с несколькими требованиями — до 4 предложений; нет содержательного разговора — 1–2 предложения. Не нужно искусственно писать четыре предложения, если разговор простой.

---

## 8. Что брать в ключевые факты

Summary Agent выбирает максимум четыре факта по приоритету: 1) главное требование клиента; 2) бюджет/финансирование/срок, если влияют на работу; 3) ключевое ограничение или возражение; 4) готовность к действию или существенное условие; 5) важный незакрытый вопрос.

**Не включать автоматически:** адрес объекта, стоимость объекта, площадь, этаж, имя агента, имя клиента, технический канал связи, данные уже видимые в карточке, малозначимые подробности, все найденные потребности подряд.

## 9. Summary Quality Gate — главный принцип

AI и человек должны оценивать: один и тот же текст; по одним и тем же критериям; по одной и той же шкале; с одинаковыми правилами начисления баллов; на основе одинакового набора доказательств. Нельзя иметь отдельную «внутреннюю» AI-метрику, которая не соответствует форме ручной оценки.

В коде это гарантирует единственная детерминированная функция `computeQualityDecision()` (`call-summary-pipeline.ts`), через которую проходят и сырые баллы AI-джаджа, и сохранённая ручная оценка.

## 10. Единая форма оценки AI и человеком

**Пять равноценных критериев, по 20% каждый** (это прямое требование продукта — переопределяет неравные веса из более раннего черновика этой спеки):

| № | Критерий | Вес |
|---|---|---|
| 1 | Достоверность | 20% |
| 2 | Полнота критически важной информации | 20% |
| 3 | Полезность для агента | 20% |
| 4 | Договорённости и следующий шаг | 20% |
| 5 | Формат, структура и краткость | 20% |

## 11. Единая шкала оценки

Дискретная шкала 0–4 на каждый критерий:

| Балл | Значение |
|---|---|
| 4 | Полностью соответствует |
| 3 | Есть одно несущественное замечание |
| 2 | Есть существенный недостаток, но summary остаётся полезным |
| 1 | Серьёзная ошибка, требуется переработка |
| 0 | Критерий не выполнен |

Пересчёт: `criterion_score = raw_score / 4 × 100`. Итог: `Overall Score = Достоверность×0,20 + Полнота×0,20 + Полезность×0,20 + Следующий шаг×0,20 + Формат×0,20`.

## 12. Детальная рубрика Quality Gate

### 12.1. Достоверность — 20%
*Все ли факты, выводы и цитаты summary подтверждены транскрибацией и JSON?*

| Балл | Критерий |
|---|---|
| 4 | Все утверждения подтверждены, роли и цитаты корректны |
| 3 | Есть одна неточная, но не изменяющая смысл формулировка |
| 2 | Есть существенная неточность или неподтверждённое утверждение |
| 1 | Несколько ошибок, перепутаны роли или искажён итог |
| 0 | Summary в значительной части не соответствует разговору |

**Блокирующие ошибки** (при наличии любой из них итог не может быть выше 60%): перепутана роль клиента и агента; придуман факт; искажён бюджет; искажён срок; неверно указана договорённость; клиенту приписано предложение агента; цитата изменяет смысл сказанного. В коде — любой `issue` с `critical: true`.

### 12.2. Полнота — 20%
*Передано ли всё критически важное, необходимое агенту для продолжения работы?* Проверяется наличие (если было в разговоре): цели обращения, основной потребности, ключевых требований, бюджета/финансирования/срока, важного ограничения/возражения, результата разговора, незакрытых вопросов.

| Балл | Критерий |
|---|---|
| 4 | Вся критически важная информация отражена |
| 3 | Пропущена одна второстепенная деталь |
| 2 | Пропущен один важный смысловой блок |
| 1 | Пропущено несколько важных блоков |
| 0 | Summary не передаёт сути разговора |

### 12.3. Полезность для агента — 20%
*Позволяет ли summary быстро понять клиента и продолжить работу без прослушивания разговора?*

| Балл | Критерий |
|---|---|
| 4 | Ситуация понятна сразу, выделены приоритеты клиента |
| 3 | Summary полезно, но есть небольшая перегруженность или неясность |
| 2 | Контекст понятен частично, агенту придётся открыть транскрибацию |
| 1 | Summary слабо помогает продолжить работу |
| 0 | Summary практически бесполезно |

### 12.4. Договорённости и следующий шаг — 20%
*Понятно ли, что будет дальше, кто отвечает за действие и когда оно должно произойти?*

| Балл | Критерий |
|---|---|
| 4 | Корректно указаны действие, ответственный, срок и канал, если они были согласованы |
| 3 | Шаг понятен, но отсутствует одна необязательная деталь |
| 2 | Следующий шаг отражён неполно или недостаточно конкретно |
| 1 | Следующий шаг искажён или смешан с предложением |
| 0 | Договорённость отсутствует или указана неверно |

Если в разговоре договорённости не было, корректная формулировка: «Конкретный следующий шаг по итогам разговора не согласован». За это оценка не снижается.

### 12.5. Формат, структура и краткость — 20%
*Соответствует ли summary утверждённому формату и удобно ли оно читается?*

| Балл | Критерий |
|---|---|
| 4 | Кратко, структурировано, естественно, без дублей |
| 3 | Есть небольшая стилистическая или форматная проблема |
| 2 | Есть повторы, перегруженность или лишние сведения |
| 1 | Текст сложный, длинный или плохо структурирован |
| 0 | Формат полностью нарушен |

## 14. Пороговые решения

| Итог | Решение |
|---|---|
| ≥95% и нет блокирующих ошибок | `PASS` |
| 90–94% | `PASS_WITH_MINOR_ISSUES` |
| 80–89% | `REGENERATE_SUMMARY` |
| <80% | `REVIEW_REQUIRED` |
| Техническая ошибка | `TECHNICAL_ERROR` |

Для MVP разрешён только один повтор Summary Generator. Если после повторной генерации результат остаётся ниже порога — ручная проверка (`REVIEW_REQUIRED`), без второго авто-повтора.

## 15. Как добиться расхождения AI и человека не более 5%

Это процесс калибровки на golden dataset, а не то, что достигается одной реализацией кода:

1. **Golden Dataset** — минимум 50 звонков (желательно 100), разные типы и длина разговоров, хорошие и плохие summary, простые и конфликтные кейсы. Для каждого звонка: транскрибация, JSON трёх этапов, эталонное summary, ручная оценка, комментарий оценщика, критические ошибки.
2. **Двойная ручная оценка** — каждое summary независимо оценивают минимум два человека; `Human Score = средняя оценка двух экспертов`; при расхождении более 10 баллов — арбитраж третьим экспертом.
3. **Оценка AI** — AI получает ту же форму, те же инструкции и те же доказательства; сравниваются `AI Overall Score`, `Human Overall Score`, разница по каждому критерию, совпадение критических ошибок.

Целевые метрики: средний Human Score ≥95%; средний AI Score ≥95%; средняя абсолютная ошибка AI vs Human ≤5 п.п.; 90-й перцентиль расхождения ≤10 п.п.; совпадение решения PASS/FAIL ≥95%; совпадение блокирующих ошибок ≥95%; согласие людей между собой ≥90%.

**Важная корректировка цели.** Не каждое summary обязано получать выше 95% — если входные данные неполные, звонок бессодержательный или extraction ошибся, корректный Quality Gate обязан поставить низкую оценку. Правильная цель: не менее 95% summary проходят порог качества после максимум одной генерации, а оценка AI отличается от согласованной ручной оценки не более чем на 5 п.п. в среднем. Иначе Quality Gate начнёт искусственно завышать оценки, чтобы выполнить KPI.

## 16. Ручная форма оценки

Человек должен видеть: транскрибацию, итоговое summary, пять критериев, оценку 0–4 по каждому критерию, поле комментария, возможность отметить тип ошибки, кнопку «Критическая ошибка». **AI-оценка показывается только после сохранения человеческой оценки** — иначе она влияет на оценщика. Это реализовано в `call-summary-pipeline-panel.tsx` явным UI-гейтом.

**Справочник типов ошибок** (одинаковый для AI Judge и человека): `FACT_INVENTED`, `FACT_DISTORTED`, `ROLE_CONFUSION`, `CRITICAL_FACT_MISSING`, `WRONG_CLIENT_NEED`, `WRONG_OUTCOME`, `WRONG_NEXT_STEP`, `QUOTE_INACCURATE`, `CRM_DATA_DUPLICATION`, `VERBOSE`, `UNCLEAR_LANGUAGE`, `FORMAT_VIOLATION`.

## 17. История запусков и отчётность

Каждый запуск нового pipeline сохраняется в общей истории запусков (`usePlaygroundTestRunStore`) и отображается в существующем Дашборде, отфильтрованный по продукту («Анализ звонков v2» — отдельная строка в селекторе «Продукт»). Статистика не смешивается со старым pipeline, потому что у каждого продукта свой `projectId`.

Для каждого запуска сохраняется (поле `report` в `PlaygroundTestRun`, JSON без ограничения по схеме): входная транскрибация, JSON каждого этапа (`facts`/`needs`/`outcome`/`summary`), AI-оценка (`aiQualityReport`), количество повторов Summary Generator, длительность (`durationMs`), использованные модели (внутри отчётов этапов), токены и стоимость (`tokens`/`costUsd`), технические ошибки (`technicalError`), версия pipeline и промтов (`evaluation_version` внутри отчёта Quality Gate).

**Осознанно вне рамок этой версии:** отдельный раздел «Оценка Summary» (`/reports`, `/review`) не дублируется под новый pipeline — тот раздел жёстко завязан на словарь первого pipeline и не имеет product-scoping. Ручная оценка и сравнение AI/человек для нового pipeline живут прямо в его собственной панели в Песочнице.
